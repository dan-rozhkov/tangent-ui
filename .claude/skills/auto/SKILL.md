Ты выполняешь задачу **`$ARGUMENTS`** в автопилот-режиме по фиксированному воркфлоу этого репозитория. Работай до конца без остановок на подтверждение (полный автопилот), но соблюдай гейты качества ниже.

## Контекст репозитория

- `arc-ui/` — один git-репозиторий (Tangent UI: галерея анимированных React-компонентов). Next.js с изменённым API: перед кодом читай `AGENTS.md` и нужный гайд в `node_modules/next/dist/docs/`. Стек: Tailwind v4, Motion (`motion/react`), Base UI, иконки `@mynaui/icons-react`.
- Компонент живёт в `components/ui/<name>.tsx`, его демо — в `components/demos/<name>.tsx`. После добавления демо нужно запустить `npm run gen:demos` (перегенерирует `components/demos/index.ts`) и добавить запись в `lib/catalog.ts`.
- Конвенции, которые должны соблюдать субагенты:
  - морф-техника как в `components/ui/action-morph.tsx` и `components/ui/toolbar-menu.tsx`;
  - `useMotionTokens()` из `@/lib/motion-tokens-context`;
  - `useReducedMotion` из `@/lib/reduced-motion`, **не** из `motion/react`;
  - цвета только из токенов, светлая и тёмная темы (тема задаётся через `data-theme` на `<html>`);
  - **никаких focus ring** — это продуктовое решение, записано в `app/foundation.css`.
- Проверки перед пушем: `npm run lint && npm run typecheck && npm run build`. Тестов нет. Визуальную проверку делай через Playwright (он есть в `node_modules`) против dev-сервера:
  - dev-сервер не убивай и второй не запускай; если его нет, подними `npx next dev -p 3100` в фоне;
  - Playwright-скрипт клади dot-файлом в корень репо, после прогона удаляй;
  - скриншоты сохраняй в scratchpad и **смотри их сам** через Read.
- Референсы (pin.it, savee, видео): вытаскивай кадры через `curl` и `ffmpeg` в scratchpad, разбирай переходы покадрово и только потом пиши ТЗ.

## Шаги

### 1. Брейншторм / план
Если задача содержит хоть каплю неоднозначности в требованиях или дизайне, сначала вызови `superpowers:brainstorming`, затем при необходимости `superpowers:writing-plans`. Явно механические или точечные правки можно делать сразу, кратко назвав план. Исследование (референсы, конвенции кода, API существующих компонентов) делаешь ты: из него получается точное ТЗ для субагента.

### 2. Делегируй субагентам на Sonnet
- Реализацию отдавай через `Agent` **с `model: "sonnet"`**, `subagent_type: "general-purpose"` (или `Explore`/`Plan`, где уместно).
- **Независимые** куски запускай параллельно — несколько `Agent`-вызовов в одном сообщении. Зависимые — последовательно.
- Если параллельные субагенты могут править одни и те же файлы, явно разведи скоупы. Общие файлы — `components/demos/index.ts` и `lib/catalog.ts`. Скажи субагентам перечитывать их перед правкой и вставлять ровно одну строку. Если разделить нельзя, дай `isolation: "worktree"`.
- В промпт субагенту зашей:
  - точный скоуп и список файлов, которые можно трогать;
  - конвенции из раздела выше;
  - требование прогнать lint и typecheck, а также Playwright-проверку со скриншотами в обеих темах;
  - что вернуть: список изменений, результаты проверок, пути к скриншотам, сомнения.
- Субагенты **не** делают git-операций: коммит и пуш делаешь только ты.

### 3. Ревью через /code-review
Когда изменения собраны, сам посмотри скриншоты субагента. Затем вызови `Skill` с `code-review` и уровнем по масштабу: `medium` для точечных правок, `high` для крупных. Дождись находок.

### 4. Почини находки
Реальные замечания ревью почини новым Sonnet-субагентом, а однострочные правки можно сделать самому. Ложные замечания отсеивай, вслепую не чини (`superpowers:receiving-code-review`): например, не добавляй focus ring вопреки продуктовому решению. Если правки существенные, повтори ревью.

### 5. Верификация перед коммитом
Перед коммитом прогони и покажи вывод `npm run lint && npm run typecheck && npm run build`. Не заявляй «готово», пока не увидел зелёный вывод (`superpowers:verification-before-completion`). Если что-то красное, вернись к шагу 4. Перед коммитом убедись, что в корне не осталось временных dot-скриптов и посторонних файлов.

### 6. Commit + push в main (делаешь ты, основной агент)
- Стейдж только файлы задачи (`git add <пути>`), а не `git add -A` вслепую. Если параллельно идёт другая работа в том же дереве, проверь, что в коммит не попали чужие правки.
- Осмысленное commit-сообщение должно заканчиваться строкой:
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`
- `git push origin main`.

### 7. Итог
Кратко на русском: что сделано, short SHA запушенного коммита, что осталось или отложено, какие пункты ревью сознательно не исправлены и почему. Если по ходу всплыло что-то важное для памяти проекта, предложи записать.

## Правила
- Если ты заблокирован (нужен доступ или решение, которое может принять только пользователь, или задача расходится с фактами кода), **остановись и спроси**, не выдумывай обходной путь.
- Не снижай пороги линта и типов ради зелёного прохода.
- Не давай субагентам делать `git stash`, `git reset` или `git checkout` в общем дереве.
